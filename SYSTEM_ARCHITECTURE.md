# SYNAPSE — System Architecture & Deep-Dive Technical Overview

SYNAPSE is an advanced, local-first Agentic IDE designed to transform natural language requirements into production-ready full-stack applications. This document provides a comprehensive technical breakdown of every subsystem, explaining the "What," "How," and "Why" behind the architectural decisions made during development.

---

## 1. Multi-Agent Orchestration (The Brain)

The "Agentic" nature of SYNAPSE is founded on a phased, multi-agent orchestration model. Instead of treating code generation as a single "one-shot" task, the system employs a specialized pipeline where different AI agents fulfill distinct roles: the **Planner** creates a technical blueprint (manifest), the **Executor** translates that blueprint into source code, the **Reviewer** performs quality assurance, and the **Debugger** handles post-generation refinements. The **Orchestrator** acts as the central state machine, managing the transitions between these phases and ensuring that context (like API contracts and database schemas) is correctly propagated down the line.

We chose this multi-agent approach because LLMs demonstrate significantly higher accuracy and lower hallucination rates when confined to narrow, well-defined tasks. A single LLM call trying to generate an entire project at once often fails to close files, forgets variables, or produces inconsistent code across the frontend and backend. By splitting the work, we can use a high-intelligence model (like Gemini 1.5 Pro) for the high-level Planning phase and a high-speed model (like Llama 3.3) for the repetitive Code Execution phase. **Alternatives** considered included autonomous agents like AutoGPT, which we rejected because they are prone to infinite loops and high token costs; we opted for a structured "Chain-of-Thought" pipeline to ensure deterministic results.

## 2. Database Architecture (Persistent State)

The database layer, built on **MySQL**, serves as the immutable record of truth for the entire ecosystem. The schema is organized into four primary tables: `projects` (metadata and status), `generated_files` (the actual source code), `pipeline_steps` (the historical log of the AI's actions), and `debug_sessions` (conversational history for fixes). Every file generated by the AI is stored as a row in the `generated_files` table, creating a "Code Mirror" of the physical filesystem. This allows the frontend UI to load and edit code instantaneously without waiting for slow disk I/O operations.

We implemented this using a structured relational model because project state is highly hierarchical—a project contains many files, which are linked to specific pipeline steps. Storing code directly in the database might seem unconventional, but it allows for advanced features like "Time Travel Debugging" and instant project rollbacks. **Alternatives** like MongoDB were considered but rejected because the relational nature of code (imports/dependencies) is better represented in SQL. We chose MySQL over SQLite to ensure that the system is ready for multi-user deployments where concurrent access and high-volume writing are required.

## 3. Service Layer & API Key Rotation

The `services/` folder houses the logic for interacting with various AI providers (Groq, Gemini, NVIDIA NIM). The cornerstone of this layer is the **Multi-Key Rotation System** inside `groqService.js`. This system intelligently tracks the "Tokens Per Minute" (TPM) and "Requests Per Day" (RPD) for every configured API key. When a key hits a rate limit (429) or a payload size error (413), the service automatically marks that key for a 60-second cooldown and rotates to the next available key. This effectively combines multiple free-tier accounts into a single, high-capacity "virtual" Pro account.

This implementation was necessary because free-tier AI APIs have extremely restrictive limits (often only 12,000 tokens per minute), which is barely enough to generate a single complex file. By abstracting the AI calls behind an **AI Router**, we can also swap models on the fly—using Llama for fast backend code and switching to Gemini if we need to process a massive image or a complex UI layout. **Alternatives** included using a single paid API key, but we chose rotation to keep the system free for developers and to provide maximum resilience against provider outages.

## 4. Batch Parsing & Code Extraction Engine

The **Batch Parser** is the critical bridge between raw AI text and valid source code. When the AI responds, it often returns a stream containing explanations, markdown backticks, and multiple files all jumbled together. The parser uses a hardened, multi-stage **Regex Engine** to scan for `<FILE: path/name>` tags. It identifies the start and end of code blocks, extracts the file path, and separates the AI's explanation from the raw code. It also handles "pre-cleaning," such as stripping forbidden JS comments from `.json` files and normalizing line endings to prevent syntax errors.

We implemented a regex-based parser rather than asking for JSON output because AI models frequently "break" large JSON objects when generating more than 2,000 tokens of code. A tag-based system allows the AI to output naturally, which is much more reliable for long-form generation. **Alternatives** like asking for one file per API call were rejected because they are incredibly slow and cause the AI to "forget" the overall project context between files. The current "Loose Regex" fallback strategy ensures that even if the AI mangles the tag structure slightly, we can still extract the code safely.

## 5. The Native Queue System

To handle the intensive computational load of generating full-stack apps, SYNAPSE utilizes a **Native Queue** (`utils/queue.js`). When a user submits a prompt, it isn't executed immediately; instead, it's added to a job list. A background **Worker** process picks up jobs one by one, managing the transition from "Planning" to "Executing" to "Saving." This ensures that only one heavy AI generation is happening at a time, protecting your local CPU and preventing your API keys from hitting concurrent request limits.

The "Native" part of the name refers to the fact that we built this using standard Node.js classes rather than external dependencies like Redis or BullMQ. This keeps the installation lightweight and "zero-config" for the developer. **Alternatives** like standard async/await calls would allow multiple users to trigger generations at once, which would inevitably crash the server and cause "Token Limit Exceeded" errors across all API keys. The queue provides a predictable, orderly flow of work that ensures every project is generated with 100% of the AI's attention.

## 6. Structured Logging & SSE Feedback Loop

Visibility into the "Black Box" of AI is provided by our **Structured Logging** system and **Server-Sent Events (SSE)**. Every action—from a DB query to a key rotation—is logged with a category (e.g., `[DATABASE]`, `[WORKER]`, `[GROQ]`) and a timestamp. These logs are not just printed to the terminal; they are piped into an SSE stream that the frontend listens to. This is what powers the "Terminal" tab in the SYNAPSE dashboard, allowing you to see the AI's internal thoughts in real-time as it builds your application.

We used SSE instead of standard WebSockets because it is lighter, unidirectional, and natively supported by browsers for streaming data. It allows the backend to "push" updates to the user without the user having to poll for changes. **Alternatives** like standard REST polling would feel laggy and add unnecessary load to the server. By seeing exactly where the AI is (e.g., "Reviewing frontend/app.js"), the user feels in control and can understand exactly why a generation might be taking time, significantly improving the overall developer experience.

## 7. Runtime Management & The "Run" System

The "Run" button is powered by the **Project Process Manager**, a subsystem that handles the lifecycle of the generated applications. When a user clicks "Run," the frontend sends a request to the `/runtime/run/:projectId` endpoint. The backend identifies the project's entry point (usually `server.js`), ensures the `output/` directory exists, and then uses Node.js `child_process.spawn` to start the application in a decoupled shell. The system automatically detects if a `package.json` exists and runs a quick `npm install` check before launching the server to ensure all AI-requested dependencies are present.

We chose this approach to provide an "Instant Preview" experience similar to Replit. By spawning the project as a child process, SYNAPSE can capture the `stdout` and `stderr` streams of the running app and pipe them back into the same SSE log stream used by the agents. This means you can see your application's console logs (and any runtime errors) directly in the SYNAPSE terminal. **Alternatives** included using Docker containers for isolation, which we rejected for the local version to keep installation simple, though it remains the recommended path for cloud deployment to prevent security risks and port clashes.

## 8. The Export Engine & The "Download" System

The "Download" functionality is handled by the **Export Engine**, which utilizes the `archiver` library to package generated code for portability. When a download is requested, the system performs a recursive scan of the project's directory in the `output/` folder. It carefully filters out heavy, unnecessary folders like `node_modules` and metadata files like `package-lock.json`, ensuring the resulting ZIP file is lightweight and clean. The ZIP is then streamed directly to the user's browser as a `binary/octet-stream` response.

We implemented this streaming approach because it is memory-efficient; instead of building the entire ZIP in the server's RAM first, we "pipe" the files into the archive and immediately out to the user. This ensures that even very large projects with many assets can be downloaded without crashing the backend. **Alternatives** like generating a static download link were rejected because they require persistent storage management; our dynamic streaming approach ensures the user always gets the absolute latest version of their code, including any manual edits made in the Live Editor.
